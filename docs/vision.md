# Moment Palette ビジョン

> ステータス: 要求整理中の暫定版
>
> 最終更新日: 2026-07-18

## 1. この文書の目的

この文書は、Moment Palette が実現する体験、機能、品質、および将来の方向性を、人間とAIが共通して参照するプロジェクトの要求仕様として定めるものである。

現時点では対話による要求整理の途中であり、確定した内容に加えて、将来構想と未決事項も明示している。実装開始に必要な範囲を基準版として合意した後、この文書を起点としてOpenSpecのchangeを作成し、段階的に技術F/Sと本実装を進める。技術F/Sや画面検討で新しい制約が判明した場合は、合意の上でこの文書を更新する。

## 2. プロダクトビジョン

Moment Paletteは、その瞬間や思い出の風景をぬり絵の一部として切り取り、自分だけの一枚のアートにする、モバイル向けWebアプリである。

ユーザーは、キンカチョウ、文鳥、花などの簡単な線画テンプレートから作品を選ぶ。塗りたいエリアを選択し、カメラで身の回りの風景から気に入った部分を切り取ると、その写真がエリアの形にはめ込まれる。これを繰り返すことで、その時にいた場所、していたこと、感じていたことを一枚の作品として残せる。

色や素材の選び方に正解はない。同じテンプレートを使っても、完成する作品は誰とも重ならない。ユーザーが気軽に制作し、端末へ保存し、一言を添えてSNSなどへ共有できる体験を目指す。

将来は、その場で撮影した風景だけでなく、端末内にある過去の写真からも思い出を作品にできるようにする。

## 3. 体験設計の原則

- 説明を読み込まなくても、テンプレート選択、撮影、完成、共有まで直感的に進められること。
- 撮影操作を軽快にし、試行錯誤を妨げないこと。
- 先に撮影したエリアとの色合いや構図を確認しながら、次のエリアを撮影できること。
- すべてのエリアを埋めることを強制せず、ユーザーが満足した時点を完成とすること。
- 撮影画像を初期段階ではサーバーへ送信せず、ユーザーの端末内で作品を生成すること。
- リリース作業が制作中のユーザーを中断させず、その作品の保存・共有まで完遂できること。
- 日本語と英語のどちらでも同等の体験を提供すること。

## 4. 想定ユーザーと利用環境

### 4.1 想定ユーザー

- ログインせず、ブラウザから気軽に遊びたいユーザー。
- 散歩、旅行、日常生活など、その時の風景や気分を作品として残したいユーザー。
- 完成作品を端末へ保存したり、SNSなどへ共有したりしたいユーザー。

### 4.2 初期の正式対応環境

- iPhoneのSafari。
- iPhoneのChrome。
- AndroidスマートフォンのChrome。
- スマートフォンの縦向き表示。

PCおよびタブレットは初期段階では正式な動作保証対象外とする。対応ブラウザの具体的な最低バージョンは、実装時の技術検証を経て定める。

## 5. 基本ユーザーフロー

1. ユーザーがタイトル画面を開く。
2. Startボタンを押す。
3. アプリが最新版であることを確認し、必要な場合は再読み込みを案内する。
4. ユーザーがテンプレート一覧から線画を一つ選ぶ。
5. 制作画面で、撮影したいエリアを選ぶ。
6. カメラを起動し、スルー映像の位置と拡大率を調整する。
7. シャッターを押し、その瞬間の映像を選択エリアへはめ込む。
8. 必要なエリアについて撮影、撮り直し、リセットを繰り返す。
9. ユーザーが満足した時点で作品を確定する。
10. 完成画像を確認し、端末への保存または共有を行う。

未撮影エリアが残っていても作品を確定できる。

## 6. 画面と機能

### 6.1 タイトル画面

- アプリ名とStartボタンを表示する。
- Startを新しい制作セッションの開始境界とする。
- Start時に、読み込まれているアプリと公開中の最新版を比較する。
- 新しいバージョンがある場合は更新案内を表示し、再読み込み後に開始する。
- 制作中に強制的な更新や再読み込みを行わない。

### 6.2 テンプレート選択画面

- 配信中の線画テンプレートを一覧表示する。
- テンプレートを選ぶと制作画面へ進む。
- 初期段階ではテンプレート数を少数に絞ってよい。
- テンプレート情報は日本語名と英語名を持てるようにする。
- 将来のタグ検索、期間限定公開、公開状態の管理を考慮したデータ形式にする。

### 6.3 制作画面

- 選択したテンプレートと、塗るエリアを選択するためのUIを表示する。
- 選択中のエリアを視覚的に判別できるようにする。
- エリア選択UIの具体的な配置や操作方法は、モバイルでのプロトタイプ検証を経て確定する。
- 撮影済みエリアを再選択し、何度でも撮り直せる。
- 撮影済み画像を外し、そのエリアの初期状態へ戻すリセット操作を用意する。
- 未撮影エリアが残っていても確定操作を可能にする。

### 6.4 カメラ撮影

#### 作品確認モード

- 選択中エリアの内部に、カメラのスルー映像を表示する。
- 撮影済みの他エリアには、それぞれの撮影済み画像を表示する。
- 未撮影の他エリアには、それぞれの初期カラーを表示する。
- 他エリアの現在の仕上がりを見ながら、選択中エリアの色合いや構図を決められるようにする。

#### カメラ全体表示モード

- 切り抜き位置を調整しやすいよう、カメラ映像全体を確認できる表示を用意する。
- 切り抜かれる選択エリアの輪郭をカメラ映像へ重ねて表示する。
- 作品確認モードとカメラ全体表示モードは、ボタンをタップするたびに切り替える。
- 撮影済み画像と薄いカメラ映像を同じ場所へ重ねて見づらくする表示は避ける。

#### 撮影操作

- カメラ権限は、ユーザーがエリアを選択して初めて「カメラで塗る」操作を行った時点で要求する。
- タイトル画面、テンプレート選択時、制作画面を開いただけの時点ではカメラ権限を要求しない。
- カメラのスルー映像を表示している間だけカメラストリームを使用し、撮影完了、撮影キャンセル、画面離脱、またはアプリがバックグラウンドへ移ったときに停止する。
- 2回目以降もスルー映像を表示するためにカメラストリームを取得するが、権限が保持されていればブラウザの確認画面は表示されない。権限の保持期間はブラウザの判断に従う。
- 初回は背面カメラを使用する。
- 前面カメラと背面カメラの両方を利用できる場合は、切替ボタンを表示する。
- カメラを切り替えても、選択中のエリアと撮影済み作品の状態を保持する。
- 超広角や望遠などの個別レンズを選択する機能は、初期リリースでは提供しない。
- ブラウザが公開するカメラ情報は端末によって異なるため、正式対応環境の実機で切替動作を検証する。
- スルー映像の表示中に、ピンチ操作で拡大率を変更できる。
- ページ全体のピンチズームとは分離し、カメラ映像の切り抜きだけを操作する。
- シャッターを押した瞬間の映像、位置、拡大率を選択エリアへ固定する。
- 撮影後の確認画面は挟まず、即座に作品へ反映して制作画面へ戻す。
- 撮影結果が気に入らない場合は、同じエリアを再選択して撮り直す。

#### カメラを利用できない場合

- Permissions APIでカメラ権限を照会できる環境では、「カメラで塗る」操作時に権限状態を確認する。
- 権限状態が `denied` であると事前に判定できた場合は、ブラウザの権限確認が再表示されない可能性を説明し、ブラウザまたは端末設定で許可する方法を案内する。
- 権限状態を照会できない、または正確に判定できない環境も考慮し、事前判定だけには依存しない。
- `getUserMedia()` が `NotAllowedError` で失敗した場合も、権限が拒否または制限されているものとして同じ案内を表示する。
- 権限状態が未設定または `prompt` の場合は、カメラが必要な理由を示した上でブラウザの権限確認へ進む。
- 案内画面には、設定変更後に利用する「もう一度試す」操作を用意する。
- カメラが存在しない、他アプリが使用中、または取得に失敗した場合は、原因に応じた案内を表示する。
- カメラを利用できない状態からテンプレート選択画面へ戻れるようにする。
- 将来、写真選択や単色塗りを追加した後は、利用可能な別の塗り方へ切り替えられるようにする。

### 6.5 完成確認画面

- 各エリアへはめ込んだ撮影画像と線画を合成し、一枚の完成作品として表示する。
- 初期段階では、作品カード、フレーム、日付、画像内テキストを追加しない。
- 完成画像は端末へ保存できるようにする。
- 対応する環境では、完成画像をSNSなどへ共有できるようにする。
- アプリ内にコメント入力欄を設けない。
- `navigator.share()` を使用し、完成画像、固定の紹介文、ハッシュタグ、アプリのURLを共有先へ渡す。
- 共有前に `navigator.canShare()` を使い、完成画像ファイルを共有できるか確認する。
- ユーザーが任意のコメントを添えたい場合は、共有先の投稿画面で固定文へ追記する。
- 画像内には、固定文、ハッシュタグ、URLを描画しない。
- 画像ファイルを共有できない環境では、画像保存ボタンと、固定の紹介文、ハッシュタグ、URLをコピーするボタンを表示する。
- ユーザーが共有シートを閉じた場合はエラーとして扱わず、完成確認画面へ戻す。

共有先によっては、画像、テキスト、URLの一部が無視または統合される可能性がある。この挙動は共有先に委ね、アプリは共有可能なデータを渡すところまでを責務とする。

## 7. テンプレート仕様

### 7.1 基本構造

テンプレートは、次の要素を組み合わせて構成する。

- 背景透過の線画。
- 塗りの対象となる複数のエリア。
- テンプレートとエリアのメタデータ。
- テンプレート一覧で使用するサムネイル。

塗りエリア同士は重ならない形で定義する。背景も特別なレイヤーとして扱わず、鳥や花などの他エリアと重ならない、一つの通常エリアとして定義できる。線画は塗りエリアとは分離して作品の手前に描画する。

エリア画像にSVGとPNGのどちらを使用するかは、クリッピング精度、制作工程、ブラウザ互換性を検証して決定する。

### 7.2 エリアの初期状態

- 各エリアは初期カラーを持てるようにする。
- 初期カラーはテンプレート全体ではなく、エリア単位のメタデータとして管理する。
- 初期カラーは白に限定せず、テンプレートに応じて薄く色分けできる。
- 未撮影エリアと、撮影後にリセットされたエリアには初期カラーを表示する。
- 将来の単色塗り機能でも、同じエリア情報を利用して色を変更できる設計とする。

メタデータの概念例を次に示す。正式なスキーマではない。

```json
{
  "id": "wing",
  "name": {
    "ja": "翼",
    "en": "Wing"
  },
  "maskUrl": "regions/wing.svg",
  "initialColor": "#F3EBDD"
}
```

### 7.3 カタログ情報

テンプレートカタログは、少なくとも次の概念を表現できるようにする。

- 変更されないテンプレートID。
- アセット更新を識別するリビジョン。
- 日本語と英語の名称。
- サムネイル、線画、エリアマスクへの参照。
- エリアの一覧と初期カラー。
- 公開状態。
- タグ。
- 公開開始日時と公開終了日時。

初期段階では、Azure Blob Storage上のJSONファイルとしてカタログを管理する。カタログ内には期限付きURLそのものではなく、各アセットのBlobパスを保持する。

フロントエンドは、Azure Static Web AppsのマネージドAPIが提供する `/api/templates` を介してカタログを取得する。マネージドAPIはBlob上のカタログを読み取り、公開状態と公開期間を判定し、利用可能なテンプレート情報へ短期間・読み取り専用のSAS URLを付与して返す。フロントエンドは画面から取得処理を直接呼び出さず、テンプレート取得用の抽象化を介して利用する。

テンプレート数が少なく、更新者が一人で、一覧を一括更新する現在の運用ではCosmos DBを使用しない。複数管理者による同時編集、複雑な検索や集計、大量のテンプレート、管理画面からの頻繁な個別更新などが必要になった場合に、APIの契約を維持したままデータストアの変更を再検討する。

## 8. 完成画像の生成

- 完成画像は、ブラウザ内のCanvasなどを用いて各エリアの画像と線画を描画し、PNGとして生成する。
- DOMとCSSをそのままスクリーンショット化する方式には依存しない。
- 画像生成時にデプロイ済みCSSを追加取得する必要がない構成にする。
- 初期段階ではフレームやテキストを含まない、テンプレートの作品領域そのものを出力する。
- テンプレートと完成画像の縦横比は正方形に統一する。
- 完成画像の内部解像度は1080×1080ピクセルとする。
- 線画の輪郭と色を劣化させないため、完成画像の形式はPNGとする。

## 9. データとプライバシー

- ログイン機能を提供しない。
- サーバー上の作品履歴を提供しない。
- 撮影画像、制作途中の状態、完成作品をアプリのサーバーへ保存しない。
- 撮影画像の加工と完成画像の生成はブラウザ内で完結させる。
- ページを閉じた後の制作再開は、初期リリースでは提供しない。
- ユーザーアカウント、作品のクラウド保存、端末間同期は、現時点の将来計画にも含めない。必要性が生じた場合は、ユーザーの同意、保存対象、保存期間、削除方法を含めてビジョンを改めて定義する。

## 10. 多言語対応

- 日本語と英語をサポートする。
- UI文言をコードへ直接埋め込まず、翻訳リソースとして管理する。
- テンプレート名など、配信データ内の表示文言も日本語と英語を持てるようにする。
- 画像内へ文字を描画しない初期方針により、フォント、言語、文字数に依存する画像編集の複雑さを避ける。

## 11. 画面表示と操作の制約

- アプリはモバイルの縦向きを前提とする。
- アプリ本体は画面内に固定し、通常のページスクロールを発生させない。
- ページ全体のピンチズームを禁止し、カメラ映像の拡大縮小だけをアプリの操作として提供する。
- 端末のセーフエリアを考慮し、ブラウザUIやノッチと主要操作が重ならないようにする。
- 端末が横向きになった場合は、制作状態を保持したまま「端末を縦向きにしてください」という全面案内を表示する。
- 端末を縦向きへ戻すと、横向きにする前の状態から操作を再開する。
- Web APIによる画面方向の強制固定には依存しない。

## 12. 初期アーキテクチャ方針

### 12.1 フロントエンド

- Vue 3を使用する。
- モバイル向けのSPAとして構築する。
- UIコンポーネントライブラリ、状態管理、テスト環境などの具体的な選定は未決定である。
- 画像合成、カメラ操作、テンプレート取得などは画面コンポーネントから分離し、単体テスト可能な構造にする。

### 12.2 配信基盤

- Azure Static Web AppsのFreeプランへのデプロイを前提とする。
- フロントエンド、リリース情報、静的な設定ファイルをAzure Static Web Appsへ配置する。
- テンプレートカタログとテンプレートアセットをAzure Blob Storageへ配置する。
- Blobコンテナの匿名アクセスは無効化し、公開中のテンプレートも期限と権限を限定したSAS URLを介して読み取る。
- GitHub上のリポジトリを起点に、GitHub Actionsでビルドとデプロイを行う。
- インフラストラクチャはコードとして管理する。

### 12.3 バックエンド

- Azure Static Web Appsに統合されたマネージドAzure Functionsを使用する。
- 初期段階のAPIは、テンプレートカタログの取得とテンプレートアセットへのアクセス許可に責務を限定する。
- テンプレート一覧をフロントエンドと同一オリジンの `GET /api/templates` で提供する。
- APIは非公開BlobからカタログJSONを読み、公開状態と公開期間をサーバー時刻で判定する。
- APIは公開対象のアセットについて、短期間かつ読み取り専用のSAS URLを生成する。ストレージへの書き込み権限をブラウザへ渡さない。
- Blobへの接続に必要な秘密情報はAzure Static Web AppsのApplication Settingsで管理し、フロントエンドへ埋め込まない。
- 作品制作、画像合成、PNG生成にはバックエンドAPIを使用せず、ブラウザ内で完結させる。
- リリース情報はAzure Static Web Apps上の小さな静的JSONとして配信し、バージョン確認のためだけにAPIを呼び出さない。
- Cosmos DBは使用しない。将来データストアを変更する場合も、フロントエンドに公開するAPIの契約を可能な限り維持する。
- ローカル開発でも、フロントエンドとマネージドAPIを同一ホストの `/api` 配下として扱える環境を用意する。

### 12.4 テンプレートの運用

- 初期リリースでは管理画面を提供しない。
- 開発者がAzure Storage Explorer、CLI、または運用用の自動化処理を使って、テンプレートアセットとカタログJSONを更新する。
- テンプレートを追加・更新するときは、参照先のアセットを先に配置し、最後にカタログを更新する。
- テンプレートを公開停止するときは、先にカタログから除外し、制作中のセッションが参照する可能性のあるアセットを猶予期間後に削除する。
- カタログJSONにはスキーマバージョンを持たせ、APIで形式と参照先を検証できるようにする。
- 誤更新や誤削除から復旧できるよう、Blobの論理削除、バージョニング、または同等のバックアップ方法を検討する。
- 管理画面と管理者認証は現時点の将来計画にも含めない。必要性が生じた場合は、認証方式、更新の競合制御、監査方法、データストアを改めて設計する。

## 13. リリース中のセッション継続性

制作中に新しいバージョンがリリースされても、ユーザーは現在の作品について完成、保存、共有まで完遂できなければならない。新しい制作を始める時点では、最新版のアプリを読み込ませる。

このため、次の配信方針を採用する。Azure Static Web Appsへのデプロイ時に旧ビルドのアセットが保持されることは前提とせず、実現方式は技術F/Sで検証する。

- ビルドごとに一意なビルドIDを付ける。
- Azure Static Web Apps上の小さなリリース情報JSONによって、現在の最新ビルドIDを配信する。
- リリース情報と起動用HTMLはキャッシュさせないか、再検証を必須にする。
- Start時に最新ビルドIDを確認する。
- 制作開始後は、更新を検出しても強制再読み込みしない。
- 制作セッションに必要なフロントエンドのJavaScript、CSSおよび選択したテンプレートアセットは、制作開始時までに取得し、セッション中に公開中の最新版へ依存して再取得しない構成を目指す。
- コード分割や遅延読み込みを採用する場合は、制作中に未取得の旧ビルドアセットが必要にならないことを確認する。
- テンプレートアセットのSAS URLは、通常の制作と保存・共有を完遂できる有効期間を持たせる。有効期限内に完遂できない場合の更新方法は技術F/Sで決定する。
- カタログから除外したテンプレートアセットは即座に削除せず、想定される最長制作時間を上回る猶予期間を設ける。
- 実際のAzure Static Web Appsへ制作中に新バージョンをデプロイし、撮影、完成画像生成、保存、共有を継続できることを検証する。

CSSのファイル名からハッシュを外すことだけを基本解決策とはしない。完成画像はDOMとCSSのスクリーンショットではなくブラウザ内の描画処理で生成し、制作開始後にデプロイ先からCSSを追加取得しなくても保存・共有できるようにする。

## 14. 開発と品質の方針

- 実装前に、ディレクトリ構成、責務分割、命名規則を定める。
- 現在のフェーズと予定するchangeの順序は `docs/development-roadmap.md` で管理する。
- 画面遷移、ワイヤーフレーム、ビジュアル方針は `docs/design/` で管理する。
- 技術F/Sの結果と採否判断は `docs/spikes/` で管理する。
- Azure構成図とアーキテクチャ資料は `docs/architecture/` で管理する。
- カメラやブラウザAPIへ依存する箇所と、画像配置計算や状態遷移などの純粋なロジックを分離する。
- 可能な限り単体テストを追加する。
- iPhoneのSafariとChrome、AndroidのChromeを実機または相当環境で確認する。
- カメラ権限の拒否、カメラ非搭載、画像生成失敗、共有非対応などの異常系を考慮する。
- 導入技術が決まった段階で `.gitignore`、README、AGENTS.mdを整備する。
- Azureアーキテクチャ図を公式アイコンを用いて作成し、構成変更に合わせて更新できる形を検討する。

## 15. 段階的な提供範囲

### 15.1 基礎機能の完成点

最初の実装上の完成点は次の機能とする。ただし、この時点で一般公開するとは限らない。

- 少数の線画テンプレートから選択できる。
- カメラで各エリアへ写真をはめ込める。
- カメラ映像を拡大縮小できる。
- 作品確認表示とカメラ全体表示を切り替えられる。
- 撮影、撮り直し、リセットができる。
- 未撮影エリアがあっても完成できる。
- 完成画像を端末へ保存・共有できる。
- 日本語と英語を切り替えられる。
- 制作中のリリースをまたいでも、保存・共有まで完遂できる。

### 15.2 初期リリースまでに追加する可能性がある機能

- カラーパレットから選んだ単色による塗り。
- 端末内にある過去の写真からの切り抜き。
- テンプレートのタグ検索。
- 期間限定テンプレート。
- カードまたはフレーム付き画像の生成。

これらを初期リリースへ含めるかは、基礎機能の体験を検証した後に決定する。

### 15.3 初期リリースに含めない機能

- 一般ユーザー向けログイン。
- サーバー上の作品履歴。
- 制作途中のクラウド保存と端末間同期。
- テンプレート管理画面。

これらは現時点の将来計画にも含めず、必要性が生じた場合にビジョンから見直す。
